report_problem The Problem: LLM Hallucination in Code

LLMs like ChatGPT and Copilot can generate impressive-looking code. But there's a catch: they sometimes "hallucinate" - producing code that looks reasonable but doesn't actually work.

lightbulb The Confident Student Analogy

Imagine a student who writes eloquent exam answers with perfect grammar and confident assertions - but the facts are wrong. The writing looks good, but it's not actually correct.

LLMs can be similar: they generate syntactically beautiful code that references APIs that don't exist, makes incorrect assumptions about behavior, or contains subtle bugs.

The Challenge: How do you get the productivity benefits of LLM code generation while eliminating the risks of hallucination? Meta's answer: automated verification.

lightbulb The TestGen-LLM Solution

TestGen-LLM doesn't just generate tests - it improves existing tests. It takes human-written test classes and extends them with additional test cases that cover corner cases the humans missed.

Filter 1: Does It Build?

The most basic check: can the generated code actually compile? This catches:

  • Syntax errors
  • References to non-existent classes or methods
  • Import issues
  • Type mismatches

Filter 2: Does It Pass Reliably?

A test that builds might still fail. This filter runs the test 5 times and requires it to pass every time. This catches:

  • Flaky tests: Tests that sometimes pass, sometimes fail
  • Wrong assertions: Tests that check for the wrong values
  • Environment dependencies: Tests that only work in certain conditions
Why 5 runs? Flaky tests are a major problem in industrial software. By requiring 5 consecutive passes, TestGen-LLM avoids introducing flakiness - one of the most hated problems in testing.

Filter 3: Does It Add Coverage?

A passing test might just repeat what existing tests already do. This final filter measures code coverage and only accepts tests that cover new lines of code.

tips_and_updates Why Coverage Matters

Coverage isn't just about numbers. It's used as a proxy for semantic uniqueness. If a new test doesn't cover any new code, it's probably testing the same thing as existing tests. Requiring new coverage ensures the test adds genuine value.

The Prompts Used

TestGen-LLM tried four different prompting strategies:

extend_coverage:
"Here is a Kotlin unit test class and the class that it tests: {test_class} {class_under_test}. Write an extended version that includes additional unit tests that will increase the test coverage."
corner_cases:
"...Write an extended version that includes additional unit tests that will cover corner cases missed by the original..."
extend_test:
"Here is a Kotlin unit test class: {test_class}. Write an extended version that includes additional tests to cover some extra corner cases."
(Note: This one doesn't even need the class under test!)

school Lessons Learned

What Worked Well

thumb_up Strengths

  • Style matching: LLM copied the human test style perfectly
  • Corner cases: Found edge cases humans missed
  • Guarantees: Filters eliminated all hallucination
  • Ensemble: Different prompts found unique tests
  • Documentation: Auto-generated coverage reports

construction Areas for Improvement

  • Self-plagiarism: LLM often generated near-identical tests
  • Trivial tests: Sometimes tested obvious things
  • TODO comments: Occasionally left placeholders
  • Coverage granularity: Only line coverage, not branch

Surprising Findings

psychology LLMs Are "Fashion Followers"

The LLMs closely mimicked the existing test style - including naming conventions, comment patterns, and even bespoke assertion utilities. This is a feature, not a bug! Tests that match the existing style are easier for engineers to review and maintain. However, it also means LLMs can pick up bad habits from the training data.

lightbulb The "Minimal Context" Surprise

One prompting strategy (extend_test) worked with only the test class - without even seeing the code being tested! This is remarkable because it suggests LLMs can infer what to test just from the patterns in existing tests.

While prompts with more context performed better, the fact that minimal context works at all opens interesting possibilities for testing code that's hard to share (e.g., proprietary dependencies).

An edge case or unusual scenario that might not be covered by typical tests. Examples: empty lists, null values, maximum integers.

flag Key Takeaways

The Big Picture

LLMs can generate useful code, but hallucination is real. The solution isn't to avoid LLMs - it's to wrap them in verification systems that filter out bad outputs and guarantee quality. TestGen-LLM proves this works at industrial scale.

Five Things to Remember

  1. Filter, Don't Trust: Don't ship raw LLM output. Use automated verification (build, pass, coverage) to guarantee quality.
  2. Improve, Don't Replace: LLMs work best when extending human work, not replacing it. TestGen-LLM builds on human-written tests.
  3. Ensemble Wins: Different prompts and models find different things. Combining them beats any single approach.
  4. Style Matters: LLMs naturally match existing code style, which makes their output easier to review and maintain.
  5. 73% Acceptance Is Excellent: For automated code generation, having engineers accept nearly 3 out of 4 suggestions is a strong result.
