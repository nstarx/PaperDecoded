code What is Vibe Coding?

"Vibe coding" is a new way of programming where you simply tell an AI what you want and it writes the code for you. Instead of writing every line yourself, you give natural language instructions to AI agents like Claude Code, Cursor, or GitHub Copilot, and they handle the complex programming work.

lightbulb Think of it Like This

Imagine hiring a contractor to build a room in your house. You describe what you want: "I need a bedroom with a window facing east and a closet." The contractor builds it, and it looks great and functions perfectly. But what if they forgot to install a lock on the door? Or used a window that doesn't close properly? The room "works" but isn't safe. That's exactly what's happening with AI-generated code.

How Popular is Vibe Coding?

  • 75% of developers surveyed are already using vibe coding
  • 90% find it satisfactory for getting things done
  • Beginners are most optimistic about AI coding
  • Even Anthropic admits to "vibe coding in production"
The Hidden Danger: Users of vibe coding often don't have the ability or time to carefully examine the code the AI produces. They trust it because it works - but "working" doesn't mean "safe."

error The Security Problem

The fundamental issue is that functional correctness ≠ security. Code can do exactly what it's supposed to do while still being vulnerable to attacks.

cancel What "Working" Looks Like

  • Feature works as expected
  • All tests pass
  • No visible errors
  • Users are happy
  • Ships to production

check_circle What "Secure" Requires

  • All of the above PLUS...
  • Input validation
  • Protection against injection
  • Proper authentication
  • No timing side-channels

Why Existing Tests Don't Catch This

Previous security benchmarks had major limitations:

description Single File Focus

Only tested code in isolated files, missing how real projects span hundreds of files

chat One-Shot Generation

Tested single-turn generation, not the multi-turn agent conversations of real vibe coding

block No Environment

Didn't let AI interact with real execution environments and get feedback

science The SUSVIBES Benchmark

To properly test vibe coding security, the researchers created SUSVIBES - a benchmark that mirrors real-world coding conditions with tasks from actual open-source projects that had security vulnerabilities.

200 Real-World Tasks
77 CWE Types
108 GitHub Projects
172 Avg Lines Edited

How SUSVIBES Works

1. Find Real Vulnerabilities

Collect 20,000+ vulnerability-fixing commits from GitHub over 10 years

2. Create the Task

Go back to BEFORE the fix was applied and mask out the feature code

3. Generate Feature Request

Use AI to write a natural language description of what needs to be built

4. Test Both Ways

Run functional tests (does it work?) AND security tests (is it safe?)

lightbulb The Clever Trick

Imagine you found a house that had a broken lock, and someone fixed it. SUSVIBES goes back in time to BEFORE the fix, removes the entire door, and asks: "Please install a door here." Then they check if the new door has the same vulnerability. This ensures they're testing whether AI makes the same mistakes humans did.

bug_report Real Vulnerabilities Found

The paper documents specific security flaws that AI agents introduced. Here are examples of dangerous vulnerabilities:

timer

Timing Side-Channel Attack (Django)

The AI's password verification returns immediately for invalid users, letting attackers enumerate valid usernames by measuring response times.

link

CRLF Injection (Buildbot)

The AI's redirect handler doesn't sanitize URLs, allowing attackers to inject malicious HTTP headers and set arbitrary cookies.

code

Cross-Site Scripting (Wagtail)

External links aren't validated, letting attackers store javascript: URLs that execute when clicked.

access_time

Session Expiration Bypass

Session max_age is stored but never enforced, allowing expired sessions to remain valid indefinitely.

search Case Study: Django Password Verification

The task: Implement a secure password verification function.

What the AI wrote (vulnerable):

def verify_password(password, encoded, preferred): if password is None: return False, False # Returns immediately! if not is_password_usable(encoded): return False, False # Returns immediately! ...

What it should have been (secure):

def verify_password(password, encoded, preferred): fake_runtime = password is None or not is_password_usable(encoded) ... if fake_runtime: make_password(get_random_string(...)) # Adds fake work! return False, False ...

The secure version does extra work even for invalid inputs, making all responses take similar time. The AI version leaks information through timing differences.

shield Can We Fix It?

The researchers tried several ways to improve security. Unfortunately, none of them worked well.

message Generic Security Prompt

"Please follow security best practices" - This is already included by default but doesn't help much.

checklist Self-Selection CWE

Ask the AI to identify security risks before coding. Result: 52.5% functional (-8.5%), 9.5% secure (-1%)

gpp_good Oracle CWE Hint

Tell the AI exactly which vulnerability to avoid. Result: 56% functional (-5.5%), 10.5% secure (no change)

The Tradeoff Problem: When you push AI to focus on security, it often breaks functionality. The agents spend time on security checks but miss functional requirements. It's like a student who studied so hard for one exam that they forgot about the other one.

lightbulb Why Security Prompts Backfire

It's like telling someone "Don't think about elephants" - now they can't stop thinking about elephants. When you tell an AI "watch out for SQL injection," it might become so focused on that one thing that it overlooks the actual feature requirements or introduces new bugs while trying to be "safe."

menu_book Glossary

Vibe Coding - Programming by describing what you want in natural language and letting AI write the actual code.
CWE (Common Weakness Enumeration) - A standardized list of software security weaknesses, like "SQL Injection" or "Cross-Site Scripting."
FUNCPASS - The percentage of solutions that work correctly (pass functional tests).
SECPASS - The percentage of solutions that are both functional AND secure.
Timing Side-Channel - A vulnerability where attackers can learn secret information by measuring how long operations take.
CRLF Injection - An attack that inserts carriage return/line feed characters to manipulate HTTP headers.
XSS (Cross-Site Scripting) - An attack that injects malicious scripts into web pages viewed by other users.
Session Fixation - An attack where the attacker sets a user's session ID to a known value, then hijacks it.
SWE-Agent - An AI agent framework for software engineering tasks that can interact with code repositories.
OpenHands - An open-source platform for AI software development agents.

lightbulb Key Takeaways

1
Working ≠ Secure
Just because AI-generated code passes your tests doesn't mean it's safe. Over 80% of functional solutions contain security vulnerabilities.
2
Beginners Are Most at Risk
Those most optimistic about vibe coding (beginners) are least equipped to identify the security flaws in AI-generated code.
3
Simple Fixes Don't Work
Adding security prompts, asking AI to self-identify risks, or even telling it exactly what to avoid doesn't reliably improve security.
4
Security vs Functionality Tradeoff
When pushed to focus on security, AI agents often break functionality - they can't effectively balance both concerns.
5
Different Models, Different Weaknesses
Different AI models are better at avoiding different types of vulnerabilities, but none are good at all of them.
Bottom Line: Vibe coding is convenient but dangerous for security-sensitive applications. Human security review remains essential - don't deploy AI-generated code to production without expert security analysis.
